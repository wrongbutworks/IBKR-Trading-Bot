BouncyBot - IBKR Portable Trading Bot v3.2.1
Production-incident gap corrections: implementation and verification report

Release scope
-------------
This release fixes the three unresolved production-incident behaviors retained as
strict expected-failure sentinels by the test-hardened v3.2.0 source:

1. LSE/LSEETF timing-sensitive actions now stop at the continuous-session
   boundary rather than a later IBKR SMART liquidHours endpoint.
2. Repeated unchanged BUY preflight blockers are audit-throttled.
3. Locally blocked BUY actions use PreflightBlocked instead of SubmitFailed.

The release version is 3.2.1. The source baseline was the corrected and
incident-replay-hardened v3.2.0 archive. No unrelated strategy percentage,
position-sizing, fill-reconciliation, order-ownership, currency, reconnect,
Trade History, or GUI workflow was changed.

1. LSE/LSEETF continuous-session timing
----------------------------------------
The adapter still parses the exact qualified contract's date-specific IBKR
liquidHours and timeZoneId. For exact primary exchanges LSE and LSEETF, it now
intersects that broker window with the verified continuous session:

    Europe/London 08:00-16:30

The effective session is:

    effective open  = later of IBKR open and 08:00 London
    effective close = earlier of IBKR close and 16:30 London

This design never extends an IBKR holiday, late open, or earlier close. If the
windows do not overlap, or the verified policy cannot be applied safely, trading
fails closed.

The effective boundary is used by the existing RTH state consumed by:

- first- and last-minutes BUY guards;
- active BUY cancellation before close;
- Stage-3 profitable liquidation before close;
- Stage-4 trailing-SELL cancellation and liquidation before close; and
- RTH-only ATR observation.

RthStatus retains both the original IBKR session bounds and the effective
continuous-session bounds for diagnostics. The short RTH metadata cache is also
rechecked against the effective boundary so it cannot keep the contract marked
open after 16:30 London.

Scope limitation: this is a deliberately narrow LSE/LSEETF continuous-session
cap, not a separately maintained universal exchange calendar and not an
independent LSE holiday or special early-close calendar. IBKR's date-specific
closed day, later open, or earlier close remains authoritative. Other SMART
primary exchanges continue to use their exact IBKR session metadata.

2. BUY preflight audit throttling
---------------------------------
A persistent local BUY blocker is still evaluated and enforced on every strategy
cadence. The cycle state is still persisted, but the same blocker category for
the same cycle is now written to the audit log at most once per 60 seconds.

The throttle key is stable and contains the cycle ID and blocker category rather
than changing prices or message text. The first event is emitted immediately,
including when a deterministic monotonic clock starts at 0.0. The warning cache
remains bounded.

The delayed/non-live-data guard is evaluated before BUY price normalization in
both positive-trail and zero-trail market-BUY paths. Consequently, a persistent
delayed-data condition no longer creates one normalization audit event plus one
block audit event every strategy cadence.

3. PreflightBlocked status
--------------------------
A BUY prevented before an order intent or live broker submission now rolls back
to Stage 1 with:

    buy_status = PreflightBlocked

This applies to local conditions such as delayed/unconfirmed data, stale data,
RTH/session timing, configured hard-risk limits, local quantity/price
normalization, what-if rejection, unavailable submission prerequisites, and
local connectivity prechecks.

SubmitFailed remains reserved for an actual broker submission attempt that
raises before broker acceptance can be confirmed. A PreflightBlocked action
creates no order intent.

SQLite compatibility
--------------------
v3.2.1 adds no SQLite table, column, index, or data migration. Status columns
were already text fields and can store PreflightBlocked without schema changes.

A representative v3.2.0 EUR database was generated with the v3.2.0 code and
contained settings, a database currency lock, an active Stage-3 cycle, one BUY
order, one execution, one audit event, and one decision event. It was opened by
v3.2.1. The following remained byte-for-byte equivalent at the SQLite row/schema
snapshot level:

- 7 application tables;
- 20 application indexes;
- all table columns;
- all row counts and selected records;
- EUR database currency lock;
- exact conId, cycle stage, order identity, execution, and audit data.

Static quality-tool limitation
------------------------------
Ruff and Pyright were not installed in the offline Linux validation environment,
so this report does not claim a locally observed v3.2.1 Ruff or Pyright exit
code. All changed Python files compiled and parsed; changed-file imports were
manually audited for grouping/order and checked for unused imported bindings.
The Windows run_all_tests.bat gate remains required before building the
production executable.

External integration checks still required
------------------------------------------
Offline broker doubles and incident replays do not prove live exchange or broker
behavior. Before production use, run:

1. the full Windows run_all_tests.bat quality gate;
2. a native Windows PyInstaller executable smoke test;
3. an IBKR paper-account test with an exact LSE/LSEETF contract around the
   16:30 Europe/London continuous close;
4. ordinary USD/EUR representative contract, reconnect, order, execution, and
   commission checks.
